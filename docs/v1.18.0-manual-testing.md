# DocSync v1.18.0 manual test guide

Record the installer version, Windows version, tester, date, result, and any
failure reference for each scenario. Use two ordinary Supabase accounts and two
separate Windows user-data directories for the account and cross-device checks.

## Authentication and account isolation

1. Start with no DocSync user-data directory. Sign in with Google, complete the
   HTTPS completion page, and select **Open DocSync** if the automatic launch is
   blocked. Confirm the desktop exchanges the PKCE code and opens an empty
   account workspace.
2. Restart the app. Confirm the encrypted session restores and the same account
   workspace opens without exposing a signed-out workspace first.
3. Create a document set as Account A, sign out, and sign in as Account B.
   Account B must not see Account A's document sets. Sign out and return to A;
   A's local data must still be present.
4. Put a v1.17 `workspace` directory under the DocSync user-data directory.
   Confirm the import prompt offers **Not now** without moving or deleting the
   source. Then import it and confirm an account-scoped copy is opened while the
   original remains intact.
5. Confirm a normal user has no **Admin** control. Assign a trusted admin role
   in Supabase and sign in again; confirm the Admin foundation appears and has no
   route to document, database, or snapshot contents.

## Backup, offline use, and conflict safety

1. Create or change a document set, wait for **Backup pending**, then choose
   **Back up now**. Confirm the account cloud panel reports **Backed up** only
   after a snapshot is created, uploaded, verified, and promoted.
2. Block the Supabase endpoint. Confirm existing local data remains usable,
   mutations stay local, the status is offline or failed, and no false
   successful-backup message appears. Reconnect and use **Check cloud status**
   before retrying the backup.
3. Use the provider test fixture to return a storage-limit response. Confirm
   the status is **Storage full**, the local workspace remains usable, and it is
   not marked synced.
4. On two devices at the same cloud revision, change and back up on B, then
   change and back up on A. Confirm A reports a conflict, B's cloud head is not
   overwritten, and A's local files remain available.

## Restore and recovery

1. On Device A, back up a workspace with known document sets. On Device B use an
   empty account-local directory and the same account. Confirm the cloud backup
   is discovered and **Restore workspace** is offered rather than silently
   opening an empty workspace.
2. Restore and confirm the archive is downloaded to temporary account storage,
   hash checked, staged, validated, promoted, and opened with a fresh backend
   session. Confirm expected document sets are present after the UI refresh.
3. Exercise restore rejection with a changed archive byte, ZIP-slip member,
   corrupt SQLite database, missing manifest, and a manifest for another user.
   Each case must leave the active workspace unchanged.
4. With a clean local workspace and newer cloud revision, confirm **Update this
   computer** is offered. With local dirty work and a newer cloud revision,
   confirm no automatic restore occurs and local work is preserved.

## Release smoke test

Install the NSIS output on a clean test machine. Check Google login, restart
persistence, account switching, one backup, one cross-device restore, logout,
Admin visibility, and the HTTPS completion-page manual button. Do not record
codes, session values, tokens, private URLs, or archive contents in test notes.
