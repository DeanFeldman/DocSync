# DocSync v1.10.0 release notes

## Deep performance optimisation

DocSync v1.10.0 reduces the cost of ingesting, searching, opening, and previewing
large related Word-document sets while preserving immutable versions, recovery,
editing behavior, and document fidelity.

In the repeatable three-file, 300-block workspace benchmark, median elapsed time
improved from 5,777.51 ms to 1,360.00 ms, a 76.46% reduction. The p95 improved
from 6,021.07 ms to 1,530.22 ms.

## Persistent Microsoft Word rendering

- Reuses one hidden Microsoft Word COM instance instead of starting Word for each
  conversion.
- Serializes conversions, opens documents read-only with link updates and alerts
  disabled, and closes each document after export.
- Recycles Word after a configurable number of renders and retries once when the
  worker or COM instance fails.
- Atomically replaces cached PDFs only after a successful export, preserving the
  previous usable PDF when refresh fails.
- Tracks the exact Word process owned by the worker so ordinary application and
  backend shutdown do not terminate unrelated Word sessions.

The measured warm export median was 244.04 ms after the first Office export. The
first export remains dependent on Office startup, document complexity, fonts,
images, add-ins, and the local Windows installation.

## Lazy layout-page rendering

- PDF structure extraction no longer creates every page image.
- Each page is rasterized when its immutable page endpoint is first requested.
- Striped locks deduplicate concurrent requests for the same page.
- Cache identity includes the document version, source and PDF fingerprints,
  render engine, PyMuPDF version, mapper version, and DPI.
- Pages one and two may be prefetched opportunistically after the map is ready;
  the remaining pages stay lazy.
- Preview coordination now uses process-local events instead of repeated 80 ms
  database polling and commits.

A forty-page benchmark created zero PNG files during structural extraction. The
first explicitly requested page rendered in 24.05 ms; explicitly rendering all
forty pages took 984.28 ms.

## Faster workspace persistence and exact matching

- Prepares stable document, element, version, head, and revision rows before
  persistence and inserts them in batches.
- Retains UUID, timestamp, checksum, JSON, lineage, and immutable-version behavior.
- Rolls back database rows and staged files together when a post-insert failure is
  forced.
- Uses SQL grouping to identify only hashes shared by at least two documents before
  materializing exact-link groups.

Median persistence time improved from 3,316.86 ms to 1,015.22 ms. Exact-match
grouping improved from 1,547.49 ms to 121.46 ms.

## Indexed current-version search

Schema migration 7, `current_block_fts5`, adds a trigger-maintained SQLite FTS5
trigram index over immutable block revisions. Existing revisions are backfilled,
and document-head joins ensure results come from current versions only.

FTS selects candidates while the existing exact occurrence scanner preserves API
counts and case-insensitive behavior. Short queries, non-SQLite databases, and
SQLite builds without FTS5 use the safe substring fallback. Candidate-selection
median improved from 20.93 ms to 7.46 ms in the 50-document, 1,000-block benchmark.

## Desktop startup and asset delivery

- `npm start` launches the already-built application without a hidden `prestart`
  production build.
- `npm run dev` starts FastAPI, Vite, and Electron directly and defaults to an
  ignored `.artifacts/dev-workspace` data directory.
- Electron startup removes an inherited `ELECTRON_RUN_AS_NODE` value that can
  prevent desktop launch in development shells.
- The displayed PNG logo remains lossless but is reduced from 2,107,107 bytes to
  21,429 bytes, a 98.98% reduction.

## Compatibility and verification

- Original uploads and historical versions are never overwritten.
- Existing preview, generation, restoration, exact-match, and search semantics are
  retained.
- Failed Word refreshes preserve a good cached PDF.
- SQLite migration failure continues to restore the verified pre-migration backup.
- Automated coverage includes worker lifecycle and restart behavior, lazy page
  rendering, stale render IDs, batched rollback, exact grouping, FTS migration and
  fallback, version generation, history, restoration, and packaged-backend health.

The release gate includes 69 Python tests, 42 Node/Desktop tests, frontend
production compilation, the frozen Windows backend build, and an exact packaged
backend health smoke test. Windows, Microsoft Word, and installer acceptance steps
are listed in [the v1.10.0 manual test plan](v1.10.0-manual-testing.md).

Detailed methodology and raw measurements are available in the
[performance optimisation report](performance-optimisation-2026-08.md).
