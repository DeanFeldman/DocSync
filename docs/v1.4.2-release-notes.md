# DocSync v1.4.2 release notes

DocSync v1.4.2 is a startup-reliability hotfix for installed Windows builds. It
keeps existing local workspaces in place, removes repeated version-foundation
backfills, gives legitimate legacy-workspace preparation enough time to finish,
and displays the installed semantic version in the application header.

## Workspace startup and migration safety

- The SQLite workspace now stores completed, monotonically ordered schema
  migrations in `docsync_schema_migrations`.
- Startup applies only migrations newer than the recorded schema. A current
  workspace takes the fast version-check path and does not rebuild versions,
  document heads, editor operations, generated files, or block revisions.
- A legacy workspace is checked relationally first. A complete v1.4.1 version
  foundation is recorded without reparsing documents; incomplete older data is
  backfilled once in bounded document batches.
- Before an existing database is changed, DocSync creates and integrity-checks a
  timestamped SQLite backup in `workspace/migration-backups`. The five newest
  migration backups are retained.
- A migration and its schema identifier commit together. If migration work
  fails, DocSync rolls back and restores the active database from the verified
  backup before reporting the error.
- Startup logs named stages without document text or session secrets, making a
  slow migration distinguishable from a backend crash.

### Manual recovery

DocSync never asks you to move or delete a workspace as a normal recovery step.
If support asks you to restore a migration backup:

1. Close every DocSync window and confirm the application is no longer running.
2. Open the workspace path shown in the startup error.
3. Preserve the active `documentsync.db` under a different name.
4. Copy the requested `.db` file from `migration-backups` into the workspace and
   name the copy `documentsync.db`.
5. Restart DocSync.

Keep the original active database and backup until the workspace has been
verified. A backup failure stops migration before persisted workspace data is
changed.

## Packaged desktop supervision

- The installed application polls `/api/health` every 500 ms and allows up to
  120 seconds for legacy-workspace preparation. Development startup keeps a
  shorter timeout.
- An early backend exit is reported immediately with its exit code, signal,
  workspace path, and capped/redacted recent service output.
- A backend that remains alive but misses the readiness deadline receives a
  distinct message recommending that other DocSync instances be closed before
  retrying.
- Local port reservation is retried before startup fails, and the window is
  created only after the backend returns the expected health response.

## Installed-version badge

- A compact `v1.4.2` badge appears in the top-right header on both the home and
  workspace screens, immediately before the Light/Dark control.
- The badge has the accessible label `DocSync version 1.4.2` and themed
  light/dark styles.
- Vite injects the value from the root `package.json`. The web build fails if
  that source is missing or is not a semantic version.

## Windows build verification

Both Windows CI and tagged release workflows now:

1. build `apps/api/dist/docsync-api/docsync-api.exe`;
2. launch that exact executable against a temporary workspace and port;
3. poll `/api/health`, failing early on process exit or readiness timeout;
4. terminate the backend and remove the temporary workspace even after failure;
5. package the already-tested output into the installer.

## Verification

Automated coverage includes fresh/legacy/current schema detection, ordered
one-time migrations, pre-migration backup creation, rollback restoration,
duplicate-free repeated startup, packaged timeout/exit diagnostics, secret
redaction, badge provenance/accessibility/theme behavior, and Windows smoke-test
workflow ordering.
